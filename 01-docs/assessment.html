The job

A wrong total, written as final, is the failure

A run that stops and says why is a success. That is the policy. The rest of this document is how I keep it true when nobody is watching, and how I prove it on the desk.

The file can be a contract, an invoice, a brief, or a signed agreement. Someone drops it. The system has to say what it is, who it is with, what it is worth, and when it applies. If it cannot say that from the page, it holds the file. It does not fill the gap.

Five rules sit under every step.

  1. A required value is kept only when it is on a page I can point at.
  2. Every failure ends in a state a person can see. There is no path that continues with a hole.
  3. The file can sit unattended. Received is not approved.
  4. The thread and the row say what happened, and neither can be quietly overwritten.
  5. Who the person is, and which rows they may see, are two different checks.

A document is done when the file is stored, the identity is settled, the read has finished, the required fields have passed, each of those fields has a page, the duplicate and revision checks have passed, the current-row write has committed, the downstream view has been updated or queued, and an audit line has been written. A green execution in n8n is not that list. n8n decides the next step. It does not own the rows or the files.

The desk proves the state changes that matter: a clean invoice, the same file twice, a revised total, a blank page, and a scan whose words are not a total. The rows are in the appendix. Slack, Drive, and the mailbox are running, and they post into the same intake. The rows I can point at were submitted from the desk. A real login is not in this build. The link is still the seat.

The life of a row

Received, then a decision

The database row starts as received. The worker claims it as processing. From there it becomes accepted, held, or waiting. Accepted with nothing pointing at a newer row is current. Waiting is a yes or a no. Silence stays waiting.

The same bytes are recognised before a model call. The hash is unique in Postgres. If two uploads of those bytes arrive together, one insert wins and the other is told which document it already is. A different file with the same invoice number or contract reference does not overwrite. It waits. Yes replaces the current row and moves the old one to history in one transaction. No holds the new file. If that transaction fails, nothing has moved.

Where the work sits

The desk, the queue, the book

A person opens a page on this machine. They do not open n8n. The page knows who the link is for, asks what the file is, and shows the book: reading, current, held, history. Five cases sit on that page. Each one runs the real intake.

On this machine the path is already that shape. Intake hashes the file. The same hash is named and stopped, with no model call. Two uploads of those bytes at the same moment take one lock. The second waits, then is told the existing id. The book has PDFs and one Word file. A PNG or a JPEG has an image route. There is no photo in this book. A Word file is read as a Word file. A stated type the text disagrees with is held, and not relabelled. That check is in the judge. It is not one of the buttons. The original goes to a private bucket, a received row is inserted, the job is queued, and the person is told the file is not approved yet. The worker then claims the row, reads it, and writes accepted, held, or waiting. The browser is not holding the HTTP call open for the model.

ClamAV 1.5.4 scans the file before it is opened, and again when the worker asks the desk to read the pages. A flagged file is refused, and no row is written. If the scanner does not finish, the file is not opened. I have not put a test virus through the desk for this submission.

What built this

The model proposes. I decide.

Cursor wrote most of the code, inside the architecture above — it does not choose the architecture. ChatGPT and Claude were the reasoning partners: the failure taxonomy, the retry policy, and the column schema were argued through with them before a line was written. Neither approved a value or touched a row in Postgres. Same rule as the rest of this document: the model proposes, the person and the code decide.

Why it runs, not only reads

I build to find the break

A written design can describe a rule. It cannot tell you where that rule breaks — under a real file, a slow API, a second upload of the same bytes. I build to find the break before a reviewer does, not to argue I would have found it eventually. That is not extra effort for this exercise. It is how I harden a process: by running it, not by scoping it well and hoping the gaps stay theoretical.

Part A

Foundations

A1. Webhook, and a manual or form trigger

A webhook is a URL another system calls. The desk, Slack, Drive, and the mailbox already have the file, or a pointer to it. The workflow starts because that system posted it.

A manual trigger is the button inside n8n. I use it while I am building. It is not how finance submits a contract. A form trigger is a page n8n hosts. I would use it if I had no other page. I built the desk because the thread, the book, and the yes or no need to live on one screen. I do not want the person on an n8n URL.

A2. Waiting, and not waiting

Synchronous means the caller sits until the work is finished. Asynchronous means the caller is told the file was taken, and the work happens after that call has ended.

Intake on this build is the second kind. It stores the file, inserts received, queues the worker, and replies. The reply is that the file is not approved yet. The case buttons on the desk then watch the book until the row leaves reading. A 100-page file takes the same first reply. It must not hold a browser open. Chunking that file is still to build. The reply is not.

A3. A 429 from the model

HTTP 429 means the service asked us to slow down. It is not a bad file. A 400 is a bad request. A 401 is a bad key. I do not retry those. Retrying them makes noise and can hide a broken configuration.

The model call on this build tries four times, three seconds apart. That is a start. The policy I want is: honour Retry-After when the service sends it, then wait longer each time with a little randomness, and stop at a retry budget. Past that budget the row is held and the thread says the model service asked us to wait. Fields stay blank. An empty total is not zero.

A retry is the same document id. It must not insert a second row, and it must not accept a second current record. The id is assigned at intake, before the model is called.

A4. Self-hosted n8n, against n8n Cloud

The contracts stay on a machine we run. Queue mode, Postgres, and the bucket sit next to n8n. Execution data can contain page text. I do not want that text on someone else’s cloud as the price of not running a box. We are also not billed per execution while a worker reads a long file.

The cost of that choice is the box. Upgrades, backups, disk, the encryption key, and a worker that has quietly stopped are ours. Cloud would take that class of failure off the table. For this workload I still self-host, and I treat backups of Postgres and the bucket as part of the system.

A5. Idempotent

Doing the thing twice leaves the same result as doing it once. A double click, a retry after a timeout, a mailbox and a person both submitting the same PDF: one document, not two.

The key is the hash of the bytes. The column is unique. The lookup happens before the model. If two inserts race, one wins and the other receives the existing id. A worker that dies after the row is already accepted does not write it again. The update runs only while the row is received or processing. A second delivery of a finished document is skipped.

Who may see it

Security and access

Authentication says who the person is. Authorization says which documents and which fields they may see. On this desk, the link ?as=andre stands in for the first of those. It is a named seat in a staff map, so the department filter and the thread can be shown. It is not a login. Production removes it. The person authenticates with Google, or with the Slack identity already stored against that person, and the book is checked before the original file or a sensitive field is returned.

The header secret on the webhook stops a stranger calling n8n directly. It does not prove who the person is. The browser never receives the database password, the model key, or the storage key. Those sit outside the workflow data and can be rotated on their own.

On the desk, a projects or accounts seat does not receive payment amounts. The page does not merely hide a column that the query already returned. Those two seats currently see an empty book, because every row is finance. A superuser sees the set. The Google Sheet is a separate copy, and that copy still includes currency and totals for anyone with the link. Hiding amounts on a second sheet is not built. Nobody gets a delete. A wrong row is superseded and stays in history. The thread is append-only. Documents and rows are kept for a retention period I would write down with the company before go-live. I have not invented that period here.

Part B

The model proposes. The checks decide.

I do not treat the model’s reply as the record. It returns one JSON object. Temperature is zero. The instruction says to leave a field empty when it is not on the page, and to list a clash instead of picking a winner. Ordinary code then decides whether those values are allowed to become truth.

This build calls one route: OpenRouter, model id google/gemini-2.5-flash, temperature zero. The row stores that route. The checks do not depend on which model filled the JSON. Google’s current guidance is that new projects should prefer a newer model, and that access to 2.5 can be limited. Swapping the route is a configuration change. It is not a new book, and it is not a reason to accept a total the page does not support. The workflow also has an image route for a PNG or a JPEG. No photo is in this book. On an invoice the counterparty is the supplier, not the customer. If the person marked the type and the text looks like a different type, I hold the file and I say so. I do not relabel it. The type decides which fields are required.

For a text PDF, a required value has to appear on a page. If it does not, the field is blanked and the document is held. The row records the sentence: the total, the reference, the date, the party, and the currency, each with its page. A total with no page is not a total. A page with no text is rendered and read with Apple Vision. If it is still empty, the document is held and the page is named. If the scan comes back with words, and those words are not a total, the total stays blank. That page is not sent on as a guess. A Word file cites the section, not an invented page number.

The system does not assume the model output is correct. Unsupported or conflicting values are rejected. The model output is a candidate extraction, not the book.

Part B

One document, one current line

Postgres is the book. The Google Sheet is a copy of those columns, split into Current, Held, Reading, and History, so a revised total is not two live invoices. Each row links to a viewable copy of the file. If the sheet is down, the book is still the book, and the sync retries. The sheet is not where the workflow writes first.

This build retries the model call four times, three seconds apart. The longer wait, the randomness, and the Retry-After header are the policy above. They are not in the node yet. What is in the node is the rule that a failed call does not become an accepted row.

If the worker dies halfway through a document, the row is still processing. Queue mode is how this build runs, so a job that is not finished can be delivered again under the same document id. The write runs only while the row is received or processing. A crash cannot create a second current record. A crash after the row is already accepted is a skip, not a second approval. I have not killed a worker in the middle of a document for this submission.

Part B

A contract is a set of pages

A one-page invoice is one text block, one model call, one decision. A 100-page contract is a pile of pages. Some have text, some are scans, some are blank on purpose. The person already has the reply that the file is received and not approved. The job id is the document id. Sending the file again hits the same hash.

The worker I would run walks the pages. Text stays text. A page with no text goes to OCR. If OCR is still empty, one picture of that page, then a hold that names the page. I do not send a hundred-page scan to the vision model page after page. Pages are then grouped, about ten at a time. Each group is its own call, and each candidate keeps its provenance: which chunk, which pages, which field, which value, which source page, and a short excerpt. The merge step does not see “chunk 4 says 18,000”. It sees “chunk 4 says 18,000, from page 37”. If two chunks disagree, both values are kept and the file is held.

That chunking is not in this build. The blank-page rule is. A contract whose second page has no text is held, and the note names page 2. I would rather hold a good invoice that sat next to a blank exhibit than accept a total from a file I could not see all of.

Cost is kept down by doing the cheap work first. The hash and the duplicate check are code. OCR runs only where the page has no text. The model runs only where a person would otherwise have to interpret the page. The price list is secondary, and it moves. Prices checked on 22 September 2026. Flash is 0.30 US dollars per million input tokens and 2.50 per million output tokens. Thinking tokens are billed as output. Flash-Lite is 0.10 and 0.40.

JobRough sizeRough cost, thinking off

I split a long contract so the merge can refuse a clash, and so the browser is not the thing waiting. A few cents is not the reason. Thinking left on can also turn a cheap call into a much larger output bill, for a job that is a form. I would turn thinking off for the field pass, and I would measure that against the fixtures before I trusted it. Flash-Lite is the trial model for the cheap questions: is this page empty, does the stated type look wrong. I would not move the money fields to Lite until the same fixtures come back with the same holds and the same totals.

Part C

A person, a backfill, a quiet morning

A correction without opening n8n

A waiting row asks yes or no on the desk. A held row can be corrected there too. Each changed value needs the page it came from. Saving the review checks the fields again and does not read the file or call the model. It becomes current only when the required fields are valid and every named blank page has been acknowledged.

Ten thousand old files

An archive does not go through the afternoon door. It is a second queue. It is admitted in small batches only while no live file is still being read. A hash already on the book is skipped. A run of failed reads, or a held majority in the last archive batch, pauses it. The door stays idle until a folder is set. A waiting list of 10,000 files was shown, then rolled back. It did not spend a model call.

Healthy, without the execution log

The desk shows whether n8n, the book, Redis, the bucket, and the sheet answer. It also shows today’s model spend, and how many pages could not be read. On 23 September 2026 that line reported all five up, two pages that could not be read, and about 0.002 US dollars of model spend. The superuser is told when a file has been waiting to be read, when a read failed before a result came back, and when a held file has been waiting on a person. The message is sent once. When the condition clears, it is not sent again. There is no separate cleared message. A person who sent a file by email is told if it was not stored, or if it did not finish as an approved record. Silence is not a success.

Proof

Production acceptance

The primary safety measure is the false acceptance rate. A document counts as a false acceptance if it is marked current and a required value is wrong, or is not supported by the page. A false hold is a good file stopped for a person. A false acceptance is the more serious of the two. The system is biased toward holding an uncertain document.

I would not use the model’s own sense of certainty as that proof. Each fixture has an expected value for every required field, including the page. Model output is compared with that expected result before a model, a prompt, or a version is promoted. A change that improves one field and degrades another is not promoted on its own. The measures I would keep are field accuracy, required-field recall, false acceptance rate, false hold rate, OCR failure rate, duplicate rate, processing time, and cost per document. I do not have a scored set large enough to publish a rate from, and I will not invent one.

The regression set

Functional: a clean invoice, a contract, a brief. Adversarial: a blank page, a corrupt PDF, conflicting totals, an impossible date, junk JSON. Concurrency: two identical uploads at once, two revisions at once, a worker restart during processing. Dependencies: a 429, a timeout, a dead model, a dead database, a dead bucket. Scale: one 100-page document, a 10,000-file backfill, and live documents at the same time. Security: a person outside the department, a session that has expired. The five buttons cover the first slice of that list. They are the cases I will not weaken to make a demo look finished.
